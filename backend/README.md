# «Поллиноз-карта Кубани»: экспериментальный API

**Не используйте для лечения, реальных оповещений, закупок или управления покосом.** Демо-сидер генерирует синтетические полигоны, спектральные значения, погоду и пыльцевые ряды; это не данные КубГМУ, Sentinel-2 или ERA5. Оценки населения, координаты клиник и роза ветров приблизительные и не проверены. Импорт пользовательского файла не является проверкой подлинности или научной валидацией. Прогнозы и экономические показатели не откалиброваны; статистика не подгоняется к целевым значениям.

## Запуск и тесты

```bash
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
cd backend
OFFLINE=true ../.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8001
# /docs — OpenAPI
OFFLINE=true ../.venv/bin/pytest -v
```

Конфигурация: `DATABASE_URL` (SQLite WAL по умолчанию, либо `postgresql+psycopg://...`), `OFFLINE`, `MODEL_PATH`, `UPLOAD_DIR`, `FORECAST_URL`, `ARCHIVE_URL`. Сохраняйте стабильный достаточно длинный секрет в `JWT_SECRET_KEY`: в демо без него ключ генерируется случайно при запуске и JWT перестают действовать после перезапуска. В `DEMO_MODE=false` этот ключ и `EDDS_MIS_API_KEY` обязательны. PostgreSQL 16 проверен изолированным smoke-тестом (startup, наряды, фото, импорт, reset); полноценное нагрузочное и миграционное тестирование не выполнено. Модель и настройки загружаются в память процесса: пока предусмотрен **только один worker**; синхронизация модели между несколькими процессами не реализована.

## Данные и импорт

- `data_provenance` — `synthetic_demo` либо `uploaded_dataset`, `source_format` уточняет CSV/GeoJSON; прежнее поле `provenance` оставлено для совместимости API этапа 1. `uploaded_dataset` означает только пользовательский файл, а не его верификацию.
- `POST /datasets/observations/import-csv` (admin, multipart `file`) заменяет активный набор наблюдений. UTF-8 CSV: `date,pollen_count,tmax,tmin,dew,precipitation,wind_speed` или ISO `year,week,pollen_count` и необязательные метеополя. Один файл — одна гранулярность. Недельные записи не разворачиваются в вымышленные суточные. Для обучения первый год должен содержать минимум 10 записей и оба класса относительно порога 10. Отчёт оценивает только более поздние годы, а недоступные метрики возвращает как `null`.
- Пропущенные метеопризнаки и промежутки GDD восполняются **синтетической** климатологией; недельные температуры для GDD повторяются в пределах соответствующей недели. Даже при загруженных измерениях пыльцы признаки могут быть синтетическими. Набор пыльцы не заменяет локальную климатологию. `/weather/forecast` GDD всегда использует синтетическую базу Краснодара.
- `POST /datasets/hotspots/import-geojson` (admin) заменяет очаги при отсутствии нарядов. Полигон WGS84 с `area_ha` и `B04`, `B08`, `B11` либо `NDVI`. Площадь предоставлена оператором и не проверяется по геометрии. Для NDVI-only реконструируются численные эквиваленты для расчёта индекса, а в API исходные каналы и NDMI обозначены как отсутствующие. Геометрии и площадь не проверяются на реальное расположение очагов. Доступны шаблоны через `/datasets/templates/{kind}`.
- `POST /datasets/reset-demo` восстанавливает оба демо-набора. При существующих нарядах необходим `?confirm_delete_work_orders=true`: это **удалит записи всех нарядов**. Фотографии при этом не удаляются, другие таблицы и погодный кэш сохраняются.
- `POST /weather/sync` (admin/dispatcher) пытается синхронизировать погоду; при `OFFLINE=true` сеть не вызывается. При неудаче источник может быть и синтетическим, а не настоящим кэшем ERA5. Внешняя доступность Open-Meteo в данном окружении не гарантирована.

## Доступ и безопасность

В демо включены 5 заранее созданных аккаунтов с общим публичным паролем; список — `/auth/demo-accounts`. Регистрация создаёт только роль patient. Пароли хешируются PBKDF2, защищённые операции требуют JWT и соответствующую роль. В недемонстрационном окружении используйте `DEMO_MODE=false`, задайте `JWT_SECRET_KEY` и `EDDS_MIS_API_KEY`. При этом список демо-аккаунтов недоступен, сидер пользователей отключён, а старые демо-логины и JWT заблокированы. Для создания собственных привилегированных пользователей используйте `python -m app.create_user` (см. корневой README). Отсутствуют обязательные для эксплуатации управление согласиями, шифрование медицинских данных, централизованный аудит, защита от перебора, разграничение врачей по прикреплённым пациентам и полноценные миграции. Фото доступны только через `GET /work-orders/{id}/photos/{before|after}` с JWT администратора, диспетчера или назначенной бригады; публичного `/uploads` нет. Токены и фото требуют HTTPS и дополнительной защиты. Нельзя считать этот backend готовым к работе с реальными персональными/медицинскими данными.

## Наряды, расчёты и оповещения

Оптимизатор ранжирует целые участки по удельному риску и отдаёт кривую накопления. Предполагаются линейная стоимость и работа в каждый календарный день; точного дискретного решения knapsack и фактических ставок контракта нет. Планировщик распределяет целые дни по реально существующим аккаунтам бригад; при нехватке времени участки остаются нераспределёнными. Закрытие требует статус `in_progress`, фотографии JPEG/PNG, полный покос и геозону 500 м; близость определяется до геометрии в локальной метрической проекции. Дельта считается на указанную в ответе дату модельного сценария, а не является измеренным эффектом. Запоздалый покос учитывает выброс в день работ; эффект покоса не переносится на следующие годы.

Персональные прогнозы складывают оценку городской ML-модели и локальный гауссов вклад: это не калиброванная клиническая модель и сумма может учитывать одни и те же источники дважды. Численности диспансерных когорт клиник неизвестны, поэтому в демо указаны нули, а число активных подписок вычисляется по БД.

`/alerts/send` и `/alerts/dispatch` — явные ручные действия врача/администратора; dispatch проверяет активные подписки и может моделировать другие даты без реальной отправки. По умолчанию доставка отключена; статусы `not_configured` и `logged_offline_demo` не означают отправку. Реальный Telegram-вызов возможен только при `TELEGRAM_BOT_TOKEN` и явном `ENABLE_LIVE_TELEGRAM=true`, что небезопасно до валидации. SMS-провайдер не подключён; записи SMS имеют `not_configured` в `/send` или `logged_offline_demo` в `/dispatch`. Автоматического планировщика, повторной доставки и гарантий exactly-once нет. Оповещение содержит медицинский дисклеймер и не является назначением. В исходном запросе спецификация этой части обрывалась; дополнительные правила интеграции потребуют уточнения.

`GET /api/v1/integrations/edds-mis-feed` доступен администратору/диспетчеру с JWT либо по `X-API-Key`, равному серверной переменной `EDDS_MIS_API_KEY`; без JWT и без настроенного ключа возвращается 503. `GET /auth/brigades` выдаёт диспетчеру/администратору идентификаторы активных бригад для распределения нарядов. Сводка содержит модельный индекс риска, а не клинические измерения.
